# Contributing & Local Setup — Nexus WP Parent Theme

A step-by-step guide to get a new developer from a fresh clone to a working, lint-clean
local environment. It reflects this project's actual tooling and conventions — not a
generic WordPress tutorial.

> Before writing code, skim the project rules in [`agent-rules.md`](./agent-rules.md) and
> the documentation matrix in [`docs/README.md`](./docs/README.md). The deep-dive specs
> under `docs/` are authoritative for each area.

---

## 1. Prerequisites

| Tool | Minimum | Notes |
| :--- | :--- | :--- |
| **PHP** | 8.1 | The theme's floor is PHP 8.1. A newer 8.x is fine for tooling. |
| **Composer** | 2.x (current) | Runs on PHP; an old Composer on a new PHP throws deprecation errors — upgrade it. |
| **Node.js** | LTS (18+) | For `@wordpress/scripts`, husky, lint-staged. |
| **npm** | 9+ | Ships with Node. |
| **Git** | any recent | — |
| **gitleaks** | optional | Local secret-scan in pre-commit; skipped gracefully if absent (CI runs it regardless). |
| **WordPress** | 6.8+ | Required by core Speculation Rules, theme.json v3, Block Bindings editor UI. |

### macOS (Homebrew)

```bash
brew install php              # PHP (8.1+; latest 8.x is fine)
brew install composer         # or: brew upgrade composer  (ensure 2.x current)
brew install node             # Node LTS + npm
brew install gitleaks         # optional, enables local secret-scan
```

Verify:

```bash
php --version        # 8.1+
composer --version   # 2.x, no deprecation warnings
node --version        # LTS
```

## 2. Local WordPress Environment

You need a running WordPress 6.8+ to view the theme. Two supported paths:

- **WordPress Studio (recommended for quick local dev):** WASM + SQLite, instant spin-up, no DB container. See `docs/06-security-and-i18n/02-devops-and-i18n.md`.
  > **SQLite is dev-only.** It is a development shim, not a production target. Production always runs MySQL/MariaDB, and shipped queries must be correct against MySQL. Never assume SQLite behaviour in code.
- **Any MySQL-backed WordPress 6.8+** (LocalWP, Docker, a dev server). Required if you need to validate real `$wpdb`/MySQL behaviour.

## 3. Clone & Install

```bash
git clone <repo-url>
cd wp-multipurpose-parent-theme

composer install   # PHP_CodeSniffer + WordPress Coding Standards + PHPCompatibilityWP
npm install        # @wordpress/scripts, husky, lint-staged (also activates the git hook)
```

`npm install` runs the `prepare` script (`husky`), which registers the git pre-commit
hook. **Until you run `npm install`, the local pre-commit gate stays dormant** — CI still
enforces the gates on push, but local checks won't fire. (See
`docs/07-performance-and-qa/06-automation-setup.md`.)

> `vendor/` and `node_modules/` are gitignored and regenerated by install. The lock files
> (`composer.lock`, `package-lock.json`) ARE committed — do not delete them; they pin exact
> versions so everyone (and CI) resolves identically. CI uses `npm ci`, which requires the lock.

## 4. IDE Setup (format-on-save)

The repo ships team-shared VS Code / Kiro settings in `.vscode/` (`settings.json`,
`extensions.json`). When you open the workspace, the editor prompts to install the
**recommended extensions** — install them to enable format-on-save:

- **PHP Sniffer** (`wongjn.php-sniffer`) — runs `phpcbf` against `.phpcs.xml.dist` on save.
- **ESLint** (`dbaeumer.vscode-eslint`) — JS auto-fix on save.
- **Stylelint** (`stylelint.vscode-stylelint`) — CSS auto-fix on save.
- **Intelephense**, **EditorConfig** — PHP intelligence and consistent whitespace.

Without these extensions the settings do nothing — format-on-save needs the extension to
exist. The command-line gates (below) and CI still work regardless.

## 5. Activate the Theme

Make WordPress see the theme, then activate it in the Site Editor:

- **Symlink** the theme into your WordPress install (adjust paths):
  ```bash
  ln -s "$(pwd)/theme" /path/to/wordpress/wp-content/themes/nexus-theme
  ```
  (Or copy `theme/` there, or point Studio at this folder.)
- In WordPress: **Appearance → Themes → activate "Nexus Multipurpose"**.
- Edit globally via **Appearance → Editor** (the Site Editor) — this replaces the classic
  Customizer and Menus screens. Navigation uses the Navigation block (`wp_navigation`), not
  `Appearance → Menus`.

> The repo root contains `theme/` (the actual theme) plus `docs/`, tooling configs, and
> steering. Only `theme/` is the shippable theme; WordPress loads that subdirectory.

## 6. Daily Workflow — Commands

```bash
# PHP
composer lint        # PHPCS: WordPress + WordPress-Extra + PHPCompatibility (8.1-)
composer lint:fix    # phpcbf: auto-fix the fixable subset

# JS / CSS
npm run lint:js      # wp-scripts lint-js  (theme/src/js)
npm run lint:css     # wp-scripts lint-style (theme/src/css/**/*.css)
npm run build        # Interactivity API bundles / optional Tailwind
npm run start        # watch/build for development
```

Format-on-save handles most style issues automatically if the IDE extensions are installed;
the commands above are the explicit/CI-equivalent runs.

## 7. Quality Gates (how your work is checked)

Four layers, from fastest/local to authoritative:

1. **Format-on-save** (IDE) — auto-fixes as you save. Needs the recommended extensions.
2. **Kiro hooks** (`.kiro/hooks/`) — lint-on-save + a security/privacy checklist reminder. Kiro users only.
3. **Pre-commit** (husky + lint-staged) — lints staged files and secret-scans on `git commit`. Every dev, after `npm install`.
4. **CI** (`.github/workflows/ci.yml`) — PHPCS, JS/CSS lint, gitleaks on every push/PR. The authoritative Definition-of-Done gate; runs for everyone regardless of local setup.

**Never bypass the gates** (`--no-verify`, skipping CI). See
`docs/07-performance-and-qa/05-coding-standards.md` §9. A change that would break CI is not done.

## 8. Commit & Branch Conventions

- **Conventional Commits:** `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`.
- Work on a feature branch; open a small, focused PR with what/why and how you verified it.
- Keep PRs green: all gates in §7 must pass before merge.
- Full standards: `docs/07-performance-and-qa/05-coding-standards.md`.

## 9. Troubleshooting

| Symptom | Cause / Fix |
| :--- | :--- |
| `composer` prints PHP deprecation errors | Old Composer on new PHP. `brew upgrade composer`. |
| `composer: php: No such file or directory` | PHP not installed. `brew install php`. |
| `npm ci` fails complaining about the lock | `package-lock.json` missing/out of sync — it must be committed; run `npm install` to regenerate, commit it. |
| Pre-commit hook never runs | You skipped `npm install` (husky not registered). Run `npm install`. |
| PHPCS reports errors you expected auto-fixed | Run `composer lint:fix`; some violations are not auto-fixable and need manual edits. |
| gitleaks "not found" in pre-commit | Optional locally; it skips gracefully. Install with `brew install gitleaks` or rely on CI. |
| Format-on-save does nothing | Recommended IDE extensions not installed (see §4). |
| Query works locally but you're unsure about production | You're on SQLite (Studio). Validate against MySQL; see §2 and `agent-rules.md` §3. |
